TASK 1. Review timeout sweeper (FR15, Phase 5)
=====================================================================

What is missing
  An escalated run waits for a reviewer. If nobody answers before the deadline,
  the run must be denied and the developer told. Today nothing does that: the run
  waits forever.

What already exists (do not rebuild it)
  - devsecops/orchestrator/graph.py, request_review(): writes a REVIEW_REQUESTED
    evidence record whose payload has commit_sha and deadline_at (ISO time, UTC).
  - graph.py, human_review(): already handles a TIMEOUT verdict. It saves the
    REVIEW_VERDICT record, posts the "Review timed out: change denied" alert and
    ends the run as DENIED.
  - devsecops/orchestrator/orchestrator.py, begin_resume(approval): checks that
    the run is paused and the commit matches, and returns a function that
    continues the run. It raises ReviewNotPending if the run is not waiting.
  - The test test_ts_06_01_timeout_denies_and_notifies_the_developer already
    shows that resuming with Verdict.TIMEOUT and reviewer="system" works.

  So the only missing part is the thing that notices the deadline has passed.

What to build
  a) In devsecops/orchestrator/approval_service.py, add to ApprovalService:

       def expire_overdue(self, now: datetime | None = None) -> list[str]

     It returns the run ids it timed out. Steps:
       - evidence.list_runs() and keep the entries whose last_event_type is
         "REVIEW_REQUESTED". A paused run's last record is always that one.
       - For each, evidence.get_run(run_id), read commit_sha and deadline_at from
         that record's payload_json.
       - If deadline_at < now: build Approval(run_id, commit_sha,
         reviewer="system", verdict=Verdict.TIMEOUT), call
         orchestrator.begin_resume(approval), then call the function it returns.
       - Catch ReviewNotPending and skip that run. It means a reviewer answered in
         the same moment, and their answer wins.
       - Catch any other exception per run, log it and go on. One broken run must
         not stop the others.

     ApprovalService does not hold the evidence store yet. Give it one in
     __init__ and pass services.evidence where api/main.py builds it (line ~96).

     Leave submit() as it is. It refuses TIMEOUT from callers on purpose
     (test_fr15_nobody_can_send_a_timeout_verdict), so the sweeper must not go
     through it.

  b) In devsecops/api/main.py, start the sweeper in lifespan(), after the
     fail_interrupted_runs() line:
       - Sweep once right away. That covers deadlines that passed while the daemon
         was down.
       - Then sweep every 30 s until shutdown.
       - Run the sweep in a thread, not on the event loop. It reads SQLite and
         calls GitHub.
       - Add sweep_interval_s: float = 30 to ApiServices so tests can shorten it,
         and stop the loop cleanly on shutdown.

  c) CLAUDE.md section 2 and section 5 say the sweeper reads an "approvals" table
     with a deadline_at column. That table was never built. The deadline is
     already in the evidence store, which survives a restart, so reading it from
     there is less code and has no second copy to keep in step. Change those two
     sentences in CLAUDE.md in the same pull request. If you would rather build
     the table, say why in the pull request.

Tests to add (pass a fixed `now`; do not sleep)
  - fr15: overdue run -> status DENIED, REVIEW_VERDICT record with TIMEOUT,
    RUN_FINISHED with DENIED, the "Review timed out" alert was sent, nothing was
    deployed.
  - A run whose deadline has not passed is left alone.
  - fr15 after a restart: start the run with one Pipeline, make a second Pipeline
    on the same tmp_path (the way test_paused_review_survives_a_daemon_restart
    does it), and expire it from the second one.
  - A run the reviewer already answered is skipped without an exception.
  - Two overdue runs where the first raises: the second is still timed out.
  - Through the API (tests/integration/test_control_api.py): with a short
    sweep_interval_s and an overdue run, GET /runs/{id} ends up DENIED.

=====================================================================

Read CLAUDE.md section 10 first. It has the decisions: OpenRouter instead of

What already exists

    PolicyAgent calls it after the rules have decided. If it returns None or

  - devsecops/api/main.py line 164 builds PolicyAgent with no writer. That is the

  - anthropic 2.8.0 is already a dependency. There is no devsecops/llm/ yet.

What to build
  devsecops/llm/__init__.py
  devsecops/llm/redact.py
      redact(text) -> str. Replaces anything that looks like a secret with
      [REDACTED]: OpenRouter and Anthropic keys (sk-or-..., sk-ant-...), GitHub
      tokens (ghp_..., github_pat_...), AWS access keys (AKIA...), "Bearer <x>",
      assignments such as password= / token= / api_key= / secret=, and private
      key blocks. Keep the patterns in one named list; task 3 reuses them.
  devsecops/llm/prompts.py
      Builds the system text and the user message. The user message holds: the
      outcome, the matched rules, the top findings (tool, rule id, file:line,
      severity, message), the failing test names, and the changed file names.
      Everything from the change goes through redact() and sits in a clearly
      marked block, and the system text says that block is data, not
      instructions.
  devsecops/llm/claude_client.py
      class ClaudeClient with write_reason(decision, results) -> str | None, so
      that client.write_reason can be passed as the ReasonWriter.
        - Client: anthropic.Anthropic(base_url=CLAUDE_BASE_URL, auth_token=key,
          max_retries=0). Defaults: CLAUDE_BASE_URL https://openrouter.ai/api,
          CLAUDE_MODEL anthropic/claude-sonnet-5.5. Both from the environment;
          do not hardcode the model anywhere else.
        - One request per run, max_tokens about 1024,
          output_config={"effort": "low"}.
        - Our own retry loop: up to claude_retries retries on
          APIConnectionError, RateLimitError and 5xx APIStatusError. Other 4xx
          (401, 402 out of credits, 400) will not get better: give up at once.
        - The whole thing, every attempt and every wait, must fit inside
          claude_max_extra_delay_s (30 s), measured from the first call. Give
          each attempt a timeout of what is left of the budget. Take the clock
          and the sleep function as constructor arguments so tests need no real
          waiting.
        - Return None (template is used) when: the retries or the budget run
          out, stop_reason is "refusal", or the text is empty. Never raise.
        - Return plain text, stripped, cut to a sensible length (about 600
          characters).
        - Never log the key, the request headers or the full prompt.
  devsecops/api/main.py line 164

TASK 4. Report section: changes from the design, and known limits
=====================================================================

CLAUDE.md lists things the final report has to say. Nobody has written them down
in report form yet. Draft this section in the report document, one short
paragraph per item: what the design PDFs said, what we built, and why.

  1. Two repos instead of one (section 2, section 11 item 10). A self-hosted
     runner on a public repo would let a stranger's pull request run code on the
     team host.
  2. Claude is called through OpenRouter, not Anthropic's API (item 11). The
     request therefore goes to two recipients, OpenRouter and Anthropic (item 9).
     Say exactly what is sent, which depends on your choice in task 2.
  3. The reviewer's name (invariant 8). approve.yml sends the GitHub login of
     whoever started it, but the API itself accepts the name from any caller
     that holds the bearer token.
  4. Append-only evidence (item 8). Triggers, hash chain and file permissions
     stop the application and detect edits. They cannot stop an admin of the
     host.
  5. Pull request runs deploy (item 2). The sandbox and the rollback version can
     hold unmerged code.
  6. Daemon restart (item 12). A run in progress is closed as ERROR and is not
     resumed; there is no automatic rollback; a run cut off during checkout
     leaves no record. A run paused for review does survive.
  7. The seeded test set (item 1). 10 safe / 10 high-risk / 10 medium, and
     "risky change blocked" means "not allowed".
  8. Where the policy is read from (item 3). The host's pinned install, never
     the commit being evaluated.
